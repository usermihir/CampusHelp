# CampusHelp Authentication — Development + Production OTP Modes

Implement the CampusHelp authentication system with two clearly separated OTP delivery modes:

```text
DEVELOPMENT
    ↓
OTP generated by backend
    ↓
OTP available only in backend/server logs
    ↓
Developer enters OTP manually

PRODUCTION
    ↓
OTP generated by backend/Auth provider
    ↓
OTP sent to user's email
    ↓
User enters OTP
```

The authentication logic, OTP expiration, verification, rate limiting, and role assignment should remain consistent between both modes.

The only major difference should be **how the OTP is delivered**.

---

# 1. Existing Requirements

CampusHelp currently has two roles:

```text
STUDENT
ADMIN
```

Every user who signs up through the normal signup flow must automatically receive:

```text
role = STUDENT
```

Users must never select their role during signup.

Admins will initially be assigned manually in the database.

For example:

```sql
UPDATE users
SET role = 'ADMIN'
WHERE email = 'admin@example.com';
```

Do not expose any public endpoint that allows a user to change their own role.

---

# 2. Signup Flow

The signup flow must be:

```text
Enter email
     ↓
Request OTP
     ↓
Verify OTP
     ↓
Create password
     ↓
Create user/profile
     ↓
role = STUDENT
     ↓
Signup complete
```

Frontend:

```text
Step 1
-----------------------
IIT KGP Email
[________________]

[Send OTP]
```

Then:

```text
Step 2
-----------------------
Enter verification code

[ _ ][ _ ][ _ ][ _ ][ _ ][ _ ]

[Verify OTP]

Resend code
```

Then:

```text
Step 3
-----------------------
Create password

Password
[________________]

Confirm password
[________________]

[Create Account]
```

# 3. Development Mode

Create a server-side environment variable:

```env
APP_ENV=development
```

or preferably:

```env
OTP_MODE=development
```

Use environment configuration rather than hardcoding development behavior.

When:

```env
OTP_MODE=development
```

the system must NOT send an actual email through Resend.

Instead:

```text
User enters email
       ↓
Backend generates OTP
       ↓
OTP is securely stored temporarily
       ↓
OTP is logged to backend/server console
       ↓
Developer copies OTP
       ↓
Developer enters OTP in frontend
       ↓
Backend verifies OTP
```

Example server log:

```text
[DEV OTP]
email=user1@gmail.com
otp=583214
expires_at=...
```

### Critical security rule

The OTP must **never** be returned in the API response.

Do NOT implement:

```json
{
  "otp": "583214"
}
```

Do NOT expose it through frontend JavaScript.

The OTP should only appear in server-side development logs.

Add a clear warning to the log:

```text
[DEV ONLY] OTP generated for testing.
Never enable OTP_MODE=development in production.
```

---

# 4. Production Mode

When:

```env
OTP_MODE=production
```

the backend must send the OTP through the configured email provider.

The architecture should be:

```text
Frontend
   ↓
Backend
   ↓
Generate OTP
   ↓
Store OTP securely
   ↓
Email provider / Resend
   ↓
User email
```

The recipient must be dynamic.

Example:

```text
User A:
To = mihir@iitkgp.ac.in

User B:
To = anotherstudent@iitkgp.ac.in
```

Do not hardcode the recipient email.

The sender can be configured through environment variables:

```env
EMAIL_FROM=CampusHelp <noreply@yourdomain.com>
```

Do not expose email provider API keys to the frontend.

---

# 5. OTP Generation

Generate a cryptographically secure 6-digit OTP.

Do not use predictable generation such as:

```python
random.randint(...)
```

if the project's language/framework provides a cryptographically secure random generator.

The OTP should be numeric:

```text
000000 - 999999
```

and should support leading zeroes.

Example:

```text
042831
```

must remain a 6-digit OTP.

---

# 6. OTP Storage

Do not store plaintext OTPs in the database in a production implementation.

Use a temporary OTP record such as:

```text
email_verification_otps

id
email
otp_hash
expires_at
attempts
max_attempts
consumed_at
created_at
```

Example:

```sql
CREATE TABLE email_verification_otps (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    email TEXT NOT NULL,

    otp_hash TEXT NOT NULL,

    expires_at TIMESTAMPTZ NOT NULL,

    attempts INTEGER NOT NULL DEFAULT 0,

    max_attempts INTEGER NOT NULL DEFAULT 5,

    consumed_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

If Supabase Auth already provides secure OTP handling, prefer using Supabase's built-in functionality instead of creating this custom table.

Do not duplicate Supabase Auth's OTP system unnecessarily.

---

# 7. OTP Expiration

OTP should expire after approximately 5 minutes.

Example:

```text
Generated: 14:00
Expires:   14:05
```

After expiration:

```text
OTP → INVALID
```

Expiration must be checked by the backend.

Never rely only on a frontend countdown timer.

---

# 8. OTP Single-Use

After successful verification:

```text
consumed_at = current_timestamp
```

or use the equivalent mechanism provided by Supabase Auth.

The same OTP must not work twice.

Example:

```text
First attempt:
583214 → SUCCESS

Second attempt:
583214 → REJECTED
```

---

# 9. OTP Attempt Limiting

Allow a maximum of approximately 5 incorrect attempts.

Example:

```text
Attempt 1 → wrong
Attempt 2 → wrong
Attempt 3 → wrong
Attempt 4 → wrong
Attempt 5 → wrong
       ↓
OTP invalidated
       ↓
User must request a new OTP
```

This must be enforced server-side.

---

# 10. Resend OTP

Implement a resend cooldown.

For example:

```text
Send OTP
   ↓
60-second cooldown
   ↓
Resend allowed
```

Prevent users from repeatedly requesting OTPs.

Apply rate limiting based on appropriate identifiers such as:

```text
email
IP address
```

Do not allow a user to generate hundreds of OTP emails.

The rate limiting should apply in both development and production modes.

---

# 11. Development Mode Must Still Test Real Security Logic

Do NOT make development mode bypass OTP verification.

Bad implementation:

```text
development
    ↓
automatically verify user
```

Instead:

```text
development
    ↓
generate real OTP
    ↓
store/hash OTP
    ↓
developer gets OTP from backend logs
    ↓
developer enters OTP
    ↓
normal verification logic
```

This ensures the same verification system is tested before production.

---

# 12. Login

Normal login should NOT require OTP.

Use:

```text
Email
[________________]

Password
[________________]

[Login]

Forgot password?
```

Flow:

```text
Email + Password
       ↓
Backend verifies password
       ↓
Fetch user
       ↓
Check account status
       ↓
Create authenticated session/token
       ↓
Get current role
       ↓
Redirect
```

---

# 13. Role-Based Redirect

After successful login:

```text
role = STUDENT
      ↓
/student
```

and:

```text
role = ADMIN
      ↓
/admin
```

Example:

```text
Student:
mihir@iitkgp.ac.in
        ↓
role = STUDENT
        ↓
/student
```

Admin:

```text
admin@iitkgp.ac.in
        ↓
role = ADMIN
        ↓
/admin
```

---

# 14. Default Role

During normal signup:

```text
new user
   ↓
role = STUDENT
```

The frontend must never send:

```json
{
    "role": "ADMIN"
}
```

Even if the frontend sends this maliciously, the backend must ignore/reject it.

The backend/database should enforce:

```text
role DEFAULT 'STUDENT'
```

---

# 15. Admin Assignment

For V1, manually promote an account in the database:

```sql
UPDATE users
SET role = 'ADMIN'
WHERE email = 'admin@example.com';
```

Then that user logs in normally:

```text
Email + Password
       ↓
Database
       ↓
role = ADMIN
       ↓
/admin
```

Do not implement an admin-selection option during signup.

---

# 16. Frontend Route Protection

Protect:

```text
/student
/admin
```

Rules:

```text
Not authenticated
    ↓
/login
```

```text
Authenticated STUDENT
    ↓
/student → allowed
/admin → denied
```

```text
Authenticated ADMIN
    ↓
/admin → allowed
```

Frontend protection is only for UI/navigation.

It is NOT the actual security boundary.

---

# 17. Backend Authorization

Every protected admin API must verify the current authenticated user.

For example:

```text
GET /api/admin/users
```

must perform:

```text
Authenticate user
      ↓
Fetch current user
      ↓
Check role
      ↓
role == ADMIN?
      ↓
YES → continue
NO  → 403 Forbidden
```

Never trust a role supplied by the frontend.

For example, this must never be trusted:

```json
{
    "role": "ADMIN"
}
```

The backend must obtain the user's actual role from the trusted authentication/database source.

---

# 18. Forgot Password

Implement:

```text
Forgot password
       ↓
Enter email
       ↓
OTP
       ↓
Verify OTP
       ↓
Create new password
       ↓
Password updated
```

The same OTP rules apply:

* expiration
* single-use
* maximum attempts
* resend cooldown
* rate limiting

Do not email the existing password.

---

# 19. Environment Configuration

Create clear environment configuration.

Development:

```env
APP_ENV=development

OTP_MODE=development

OTP_EXPIRY_MINUTES=5
OTP_MAX_ATTEMPTS=5
OTP_RESEND_COOLDOWN_SECONDS=60
```

Production:

```env
APP_ENV=production

OTP_MODE=production

OTP_EXPIRY_MINUTES=5
OTP_MAX_ATTEMPTS=5
OTP_RESEND_COOLDOWN_SECONDS=60

EMAIL_FROM=CampusHelp <noreply@yourdomain.com>
RESEND_API_KEY=...
```

Never commit `.env` files containing secrets.

Add appropriate entries to `.gitignore`.

---

# 20. Prevent Accidental Production Misconfiguration

Fail safely.

If:

```env
APP_ENV=production
```

then:

```text
OTP_MODE=development
```

must cause the application to refuse startup or clearly fail configuration validation.

Do not silently run production with development OTP logging.

For example:

```text
ERROR:
Development OTP mode cannot be enabled when APP_ENV=production.
```

This is important because otherwise real user OTPs could accidentally be printed in server logs instead of being emailed.

# 21. API Design

Use a clean API structure.

For example:

```text
POST /api/auth/signup/request-otp
POST /api/auth/signup/verify-otp
POST /api/auth/signup/complete

POST /api/auth/login

POST /api/auth/password/request-otp
POST /api/auth/password/verify-otp
POST /api/auth/password/reset
```

If Supabase Auth is already handling these operations, do not create duplicate endpoints unnecessarily. Adapt the existing architecture instead.

# 22. Development Testing

Test with multiple arbitrary emails during development:

```text
mihir@test.com
user1@test.com
user2@test.com
user3@test.com
```

For each:

```text
Request OTP
     ↓
Unique OTP generated
     ↓
OTP appears only in backend console
     ↓
Enter OTP
     ↓
Verification succeeds
     ↓
Create account
     ↓
role = STUDENT
```

Example:

```text
user1@test.com → OTP 583214
user2@test.com → OTP 194827
user3@test.com → OTP 720351
```

Each OTP must be independent.

---

# 23. Important Security Tests

Verify:

```text
✓ OTP is never returned in API response
✓ OTP is not exposed to frontend
✓ OTP expires
✓ OTP cannot be reused
✓ OTP attempts are limited
✓ OTP resend is rate limited
✓ Different emails receive different OTPs
✓ Signup always creates STUDENT
✓ Client cannot assign ADMIN role
✓ Password is hashed
✓ Password hash is never returned
✓ Admin API rejects students
✓ Unauthenticated users cannot access protected routes
✓ Development OTP mode cannot run in production
✓ API keys are never exposed to frontend
```

---

# 24. Architecture

The final architecture should be:

```text
                       CAMPUSHELP
                           │
                     ┌─────▼─────┐
                     │   Signup  │
                     └─────┬─────┘
                           │
                        Email
                           │
                           ▼
                     Request OTP
                           │
                 ┌─────────┴─────────┐
                 │                   │
            DEVELOPMENT          PRODUCTION
                 │                   │
                 ▼                   ▼
          Generate OTP          Generate OTP
                 │                   │
                 ▼                   ▼
           Server logs           Resend/email
                 │                   │
                 └─────────┬─────────┘
                           │
                       User enters
                           OTP
                           │
                           ▼
                    Backend verifies
                           │
                           ▼
                    Email verified
                           │
                           ▼
                    Create password
                           │
                           ▼
                    Create profile
                           │
                           ▼
                    role = STUDENT
                           │
                           ▼
                         Login
                           │
                 ┌─────────┴─────────┐
                 │                   │
              STUDENT              ADMIN
                 │                   │
                 ▼                   ▼
             /student             /admin
```

The key design principle is:

**Development and production must use the same OTP verification logic. Only OTP delivery changes.**

Do not create separate authentication systems for development and production.
